2. PROBLEM & PRODUCT VISION

Problem: People who follow many niche Telegram channels (tech influencers, industry news, niche communities) cannot keep up with the volume. Reading every post from 10-20 channels daily is exhausting, and important information gets buried.

Solution: A Telegram bot where a user (1) selects topics of interest, (2) adds a handful of public Telegram channels they already follow, and (3) receives exactly two digest messages per day — short, scannable summaries of new posts from their channels, each ending with a Batafsil: [link] ("Read more") link pointing to the original post for anyone who wants full detail.

Product language: The end-user-facing bot interface (all messages, buttons, onboarding copy) must be in Uzbek. Code, comments, commit messages, and this document stay in English.

Core design principle — brevity over completeness: Digest messages must never feel like a wall of text. Each channel's update is summarized in 1-3 sentences maximum, never a full repost of the original content. This is both a UX requirement and a copyright-safety requirement (never reproduce full original post text — always paraphrase + link).

3. TELEGRAM COMPLIANCE REQUIREMENTS (non-negotiable)

This product must operate strictly within Telegram's rules. Design every component with these constraints in mind:

  • No unauthorized scraping abuse. Prefer the official Telegram Bot API wherever possible. For public channels the bot is not a member of, use the public t.me/s/{channel} preview endpoint only as a lightweight, low-frequency, read-only fallback — never more than a handful of requests per channel per day, with caching so multiple users tracking the same channel trigger only one fetch, not one per user.
  • Respect rate limits. All outbound bot messages must go through the official Bot API's rate limits (~1 message/sec per chat, ~30 messages/sec globally across chats). Implement a proper outgoing message queue with throttling — do not fire messages in an unthrottled loop.
  • No spam, no unsolicited messages. Users must explicitly opt in via /start and explicit channel additions. Provide a clear /stop or unsubscribe command that immediately halts all future digests for that user, respecting Telegram bot policy on user consent.
  • No full-content reproduction. Never forward or reproduce a full original post. Always summarize in your own generated words and link back to the source (https://t.me/{channel}/{message_id}).
  • Transparent identity. The bot must have a clear name/description explaining what it does and how to stop it, per Telegram bot guidelines.
  • Data minimalism. Only store what's needed to operate (channel usernames, cached post metadata, user preferences). Do not store or process users' personal Telegram account data — users only ever provide channel usernames, never their own account credentials or session.

5. BOT CONVERSATION FLOW (Uzbek UI copy — write actual bot strings in Uzbek)

  1. /start → Welcome message in Uzbek explaining what the bot does in 2-3 sentences.
  2. Interest selection → Inline keyboard with topic categories (e.g. "Texnologiya", "Startap", "Karyera", "AI", "Biznes", "Ta'lim" — make this configurable, not hardcoded) — multi-select, then a "Davom etish" (Continue) button.
  3. Channel addition → Bot asks user to send a channel username (e.g. @kanalnomi) or forward a post from the channel. Bot validates the channel is public and reachable, confirms with channel name back to user. Repeat until user sends "Tayyor" (Done) or reaches a reasonable max (e.g. 15 channels).
  4. Confirmation → Summary of selected interests + channels, explain the twice-daily digest schedule, and how to use /stop.
  5. Ongoing commands: /mychannels (list/remove), /addchannel, /interests (edit), /stop (unsubscribe, with confirmation step), /help.

Digest message format (Uzbek, example structure — keep this exact pattern in the implementation)

📰 Bugungi yangiliklar

▸ @kanalnomi
[1-2 gapli xulosa, o'z so'zlar bilan]
Batafsil: https://t.me/kanalnomi/12345

▸ @boshqakanal
[1-2 gapli xulosa]
Batafsil: https://t.me/boshqakanal/6789

Rules for the worker when building this message:

  • Skip channels with no new posts since the last digest — never send "no updates" noise.
  • If a channel has many new posts, summarize the most significant ones only (cap at ~3 items per channel per digest) rather than listing everything.
  • Never let a single digest message exceed a comfortable reading length (target under ~600 characters per channel entry; split into multiple Telegram messages only if truly necessary, never as a wall of text in one message).

6. DATABASE SCHEMA (Prisma — implement exactly, extend only if needed)

model User {
  id            String   @id @default(cuid())
  telegramId    BigInt   @unique
  username      String?
  interests     UserInterest[]
  channels      UserChannel[]
  createdAt     DateTime @default(now())
  isActive      Boolean  @default(true) // false after /stop
  digestHourUtc Int      @default(6)    // first of the 2 daily slots, configurable later
}

model Interest {
  id    String @id @default(cuid())
  name  String @unique   // e.g. "Texnologiya", "Karyera"
  users UserInterest[]
}

model UserInterest {
  userId     String
  interestId String
  user       User     @relation(fields: [userId], references: [id])
  interest   Interest @relation(fields: [interestId], references: [id])
  @@id([userId, interestId])
}

model Channel {
  id            String   @id @default(cuid())
  username      String   @unique // without @
  title         String?
  lastScrapedAt DateTime?
  isReachable   Boolean  @default(true)
  users         UserChannel[]
  posts         Post[]
}

model UserChannel {
  userId    String
  channelId String
  user      User    @relation(fields: [userId], references: [id])
  channel   Channel @relation(fields: [channelId], references: [id])
  addedAt   DateTime @default(now())
  @@id([userId, channelId])
}

model Post {
  id            String   @id @default(cuid())
  channelId     String
  channel       Channel  @relation(fields: [channelId], references: [id])
  telegramMsgId BigInt
  rawText       String?
  summary       String?  // LLM-generated short summary
  category      String?  // matched to Interest for personalization
  postedAt      DateTime?
  fetchedAt     DateTime @default(now())
  @@unique([channelId, telegramMsgId])
}

model Digest {
  id          String   @id @default(cuid())
  userId      String
  sentAt      DateTime @default(now())
  status      String   // "sent" | "failed" | "skipped_no_updates"
  postIds     String[] // posts included in this digest
}

7. QUALITY & ENGINEERING STANDARDS

  • TypeScript strict mode everywhere, no any.
  • apps/bot and apps/worker: Node.js + TypeScript, aiogram-equivalent (e.g. grammY or telegraf for Node) for bot logic.
  • apps/admin: Next.js (App Router) + TypeScript + Tailwind + shadcn/ui, protected by a simple admin-only auth (env-var credential or single admin account — this is an internal tool, not public-facing).
  • The worker's scraping/fetching layer must be isolated behind an interface (ChannelSource) so the scraping method (public preview page vs. official Bot API membership) can be swapped or run as a fallback chain without touching business logic.
  • All external calls (Telegram fetch, LLM calls) wrapped with retries + exponential backoff + timeout.
  • Structured logging (no console.log soup) — one logger utility shared across apps.
  • .env.example files in every app documenting required environment variables.
  • Unit tests for: digest-building logic, channel validation, summarization prompt formatting, rate-limit queue behavior.
  • ARCHITECTURE.md at repo root containing the Mermaid diagram from Section 4.2, plus a short written explanation of each component — this is the file a recruiter or visitor reads first.
  • README.md explaining the problem, the product, setup instructions, and a link to ARCHITECTURE.md.
